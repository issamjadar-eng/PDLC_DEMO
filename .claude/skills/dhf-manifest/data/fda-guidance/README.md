# Tier 1 — Regulatory Obligations Catalog

Structured obligations catalog used by `/dhf-manifest` to project regulatory and guidance requirements into per-DHF deliverable checklists. Each file here is an *obligation-centric* view of a single standard or guidance: what it demands, in a form the manifest builder can consume and project across a device's DHFs.

This is Tier 1 of the four-tier manifest architecture:
- **Tier 1 (here)** — regulatory obligations from FDA / IEC / ISO (what external bodies require)
- **Tier 2 — QMS obligations** — what the organization's quality system requires (lives at `docs/project/dhf-manifest/tier2-qms/` in the consuming project)
- **Tier 3 — reference DHF** — the catalog schema + dimensions used to combine tiers (lives at `../tier3-reference/`)
- **Tier 4 — project manifest** — the projected deliverable list per DHF (lives at `docs/project/dhf-manifest/tier4-project/` in the consuming project)

## Scope

### In Scope
- Structured, machine-readable obligation descriptions that `/dhf-manifest` can parse
- Clause/section references, deliverable names, applicability gates (class, device type, AI-enabled, etc.)
- Cross-references between obligations (e.g. IEC 62304 §7 risk → ISO 14971)

### Out of Scope (see instead)
- **Narrative clause distillation** — see `.claude/skills/medtech-docs/references/standards/` and `.claude/skills/medtech-docs/references/fda-guidance/` for prose-style summaries. This folder is *obligation-centric* not *clause-centric*.
- **Project-specific applicability** — `docs/external/<category>/` in the consuming project
- **Projected per-DHF deliverables** — `docs/project/dhf-manifest/tier4-project/` in the consuming project, generated by `/dhf-manifest` from these Tier-1 + Tier-2 sources through the Tier-3 schema

## Conventions

- Files are named `<source-acronym>.md`, lowercase-kebab
- Structure follows the Tier-3 schema (see `../tier3-reference/scope-schema.yml`)
- When both a prose distillation (in `medtech-docs/references/`) and an obligations file (here) exist for the same source, they are complementary not redundant — one is narrative, the other is structured

## For Claude (when grounded against a consuming project)

Agents usually want the narrative distillation in `.claude/skills/medtech-docs/references/` first — that's more readable and answers "what does the standard say." Use the obligations file here when the question is about **deliverables** — "what evidence does IEC 62304 require us to produce for Class C software?" or "which PCCP artifacts go into the 510(k) submission?" — because the obligations catalog is explicitly deliverable-indexed.
