```yaml
id: OBL-81001-001
title: "Security Risk Management Plan"
source: IEC 81001-5-1:2021 §4.2
section: "4.2 — Security Risk Management"
scope_flags: [cybersecurity, common-baseline]
topic: cybersecurity
artifact_type: plan
dhf_owner: system
min_iec62304_class: A
applies_to: [Security Risk Assessment, Risk Management Plan, Software Development Plan]
verbatim: "Integrate security risk management into the overall risk management process (ISO 14971). Security risk management must consider: confidentiality, integrity, availability. Apply throughout the entire lifecycle."
extracted_requirements:
  - Integrate security risk management with the ISO 14971 risk management process — security risks must appear in the device risk file
  - Security risk assessments must address three properties: confidentiality, integrity, and availability (CIA triad)
  - Apply security risk management throughout the entire product lifecycle (not just development)
```

**Context**: Security risk management is not a separate silo — it feeds into the integrated device risk file (ISO 14971). Security threats that could compromise patient safety (e.g., data integrity attacks on surgical guidance, ransomware disabling the system mid-procedure) are device hazards and must be treated as such. For MedTech Project, confidentiality failures (PHI exposure), integrity failures (corrupted image data affecting surgical guidance), and availability failures (offline-capable Intra-Op losing sync) each have patient safety implications.

topic: requirements
artifact_type: specification
dhf_owner: both
min_iec62304_class: A
applies_to: [Software Requirements Specification, Security Requirements]
verbatim: "Derive security requirements from: security risk assessment, regulatory requirements, intended use environment threat landscape, data protection requirements (PHI/PII if applicable). Security requirements must cover: authentication and access control, authorization and privilege management, audit logging and accountability, data confidentiality (at rest and in transit), data integrity, secure communication, software update/patch mechanisms, cryptographic controls."
extracted_requirements:
  - Derive security requirements from security risk assessment + FDA cybersecurity guidance + PHI/PII obligations
  - SRS must include security requirements covering: authentication, access control, role-based authorization, audit logging
  - SRS must cover data protection: confidentiality at rest and in transit, data integrity, encryption standards
  - SRS must address software update security: authenticated OTA update mechanism with integrity verification
  - SRS must specify cryptographic controls: approved algorithms, key management, certificate handling
```

**Context**: For MedTech Project, security requirements span all three modules differently. Management Services hosts PHI-adjacent data (case records, imaging links) requiring strict access control, audit logging, and encryption at rest. Intra-Op must maintain data integrity for surgical guidance data (a corrupted image could mislead the surgeon). OTA updates to the Intra-Op tablet are a high-risk attack surface — the update mechanism must be authenticated and integrity-verified.

extracted_requirements:
  - Apply secure design principles in the SAD: defense in depth, least privilege, secure defaults, fail secure, minimize attack surface
  - Document security architecture decisions as architectural records
  - Identify and explicitly document trust boundaries between components (SaMD/non-SaMD boundary is a trust boundary)
  - Separation of duties must be reflected in the architecture (e.g., Management Services cannot alter Intra-Op clinical data unilaterally)
```

**Context**: The MedTech Project system SAD already defines an explicit SaMD/non-SaMD boundary (5 enforcement rules). This boundary is also a security trust boundary — Management Services (cloud) communicates with Intra-Op (tablet) across an untrusted network link. The SAD must document: how data crossing this boundary is authenticated and integrity-checked, what data flows are permitted vs. blocked, and how the fail-secure principle is applied if the network link is unavailable or compromised.

  - Follow a defined secure coding standard (e.g., OWASP, CERT C, or equivalent)

  - Conduct security-focused code reviews for high-risk components
  - Track SOUP/third-party dependencies for known vulnerabilities (CVE/NVD monitoring)
```

**Context**: SOUP vulnerability management is continuous — it does not end at release. Each SOUP component in the SBOM must have a defined monitoring process. For MedTech Project's cloud-hosted components (Management Services), SOUP vulnerabilities may be patched via OTA update. For Intra-Op's tablet, the patch path is more constrained and must be planned in advance.

extracted_requirements:
  - Conduct system-level security testing before release: vulnerability scanning, penetration testing
  - Include fuzz testing for network-facing and data-parsing components (DICOM ingestion, OTA update receiver)
  - Run security regression testing after code changes that affect security-relevant components
  - Verify security controls against the CVE/NVD database — no unmitigated high-severity known vulnerabilities at release

**Context**: Penetration testing is a pre-market cybersecurity requirement for FDA submissions (referenced in FDA's premarket cybersecurity guidance). For MedTech Project, penetration testing must cover: Management Services cloud APIs, the Intra-Op tablet's network interface, the DICOM ingestion pipeline, and the OTA update mechanism. Plan penetration testing as a late-stage V&V activity (after all security controls are implemented) and include the pentest report in the 510(k) submission package.

  - SBOM must cover all software components including SOUP/third-party libraries

```

**Context**: SBOM is a mandatory pre-market cybersecurity submission artifact per FDA's 2023 cybersecurity guidance (FD&C Act §524B, effective March 2023). The SBOM must be maintained and updated throughout the product lifecycle. For MedTech Project, the system-level SBOM aggregates item-level SBOMs from all three modules. The system DHF owns the rollup SBOM; each item DHF maintains its own component-level SBOM.
