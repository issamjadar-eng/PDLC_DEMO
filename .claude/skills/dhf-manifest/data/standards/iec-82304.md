```yaml
id: OBL-82304-001
title: "Health Software Requirements"
source: IEC 82304-1:2016 §4.2
section: "4.2 — Risk Management"
scope_flags: [common-baseline]
topic: risk-management
artifact_type: plan
dhf_owner: system
min_iec62304_class: A
applies_to: [Risk Management Plan, Risk Management File]
verbatim: "Apply risk management per ISO 14971 to the health software product. Risk management must cover the full product lifecycle. Include risks from: intended use environment, interoperability, data migration, IT security."
extracted_requirements:
  - Apply ISO 14971 risk management at the product level (IEC 82304-1 mandates this; does not define its own risk process)
  - Risk management must span the full product lifecycle including maintenance and decommissioning
  - Risk assessment must include risks from: intended use environment, system interoperability, data migration, IT/cybersecurity threats
```

**Context**: IEC 82304-1 does not define its own risk management process — it defers entirely to ISO 14971. The notable extension is the explicit scope: risk management must include risks from system interoperability (MedTech Project interfaces with C-arm imaging devices and PACS systems) and data migration (patient plans migrated between software versions during PCCP changes). These are often overlooked in traditional medical device risk files.

```yaml
scope_flags: [common-baseline]
topic: software-lifecycle
artifact_type: process-record

min_iec62304_class: A
applies_to: [Software Development Plan, IEC 62304 Conformance Records]
verbatim: "Software development must conform to IEC 62304. This is where the two standards connect — IEC 82304-1 requires IEC 62304 compliance."
extracted_requirements:
  - All software development activities must conform to IEC 62304
  - IEC 82304-1 does not add development obligations beyond IEC 62304 — it mandates IEC 62304 conformance as the mechanism
  - Conformance records for IEC 62304 serve as the evidence base for IEC 82304-1 §4.3 compliance
```

**Context**: IEC 82304-1 and IEC 62304 are complementary. IEC 62304 governs the development process; IEC 82304-1 governs product-level safety across the full lifecycle. Conformance to IEC 62304 satisfies IEC 82304-1 §4.3 — there is no separate evidence needed. This means the DHF trace matrix for IEC 82304-1 §4.3 points to the same deliverables as the IEC 62304 trace.

```yaml
scope_flags: [common-baseline]

artifact_type: specification
dhf_owner: system

applies_to: [Device Description, Intended Use Statement, Software Requirements Specification]
verbatim: "Define the intended use of the health software product. Define the intended operating environment (hardware, OS, network, interfacing systems). Define the intended user profile."
extracted_requirements:
  - Define the intended use of the health software product (maps to the FDA Indications for Use Statement)
  - Define the intended operating environment: hardware platforms, OS versions, network requirements, interfacing systems (DICOM, PACS, C-arm)
  - Define the intended user profile (maps to IEC 62366-1 §5.1.1 user characterization)
```

**Context**: The intended operating environment definition is critical for MFD B because it operates on a specific tablet model in a specific OR network configuration. The operating environment must be explicitly bounded — which tablet models, which OS versions, which C-arm systems are supported, and what network conditions are required for cloud sync. PCCP changes that expand the operating environment (new tablet model, new OS version, new imaging system interface) must be evaluated for safety impact.

<a id="OBL-82304-004"></a>

```yaml
id: OBL-82304-004
title: "Product Validation Execution"
source: IEC 82304-1:2016 §5.2
section: "5.2 — Health Software Product Safety Requirements"
scope_flags: [common-baseline]
topic: requirements
artifact_type: specification
dhf_owner: both
min_iec62304_class: A
applies_to: [Software Requirements Specification, Risk Control Requirements]
verbatim: "Derive safety requirements from risk management activities. Include requirements for: data integrity, access control, confidentiality, audit trails. Address requirements for IT-network integration. Consider degraded performance modes."
extracted_requirements:
  - Safety requirements must be derived from risk management (ISO 14971) activities — not authored independently
  - SRS must include requirements for: data integrity (guidance data cannot be silently corrupted), access control (patient data access scoped to authorized users), confidentiality (PHI protection), audit trails (who accessed/modified what data)
  - Address IT-network integration requirements (what happens when cloud sync is unavailable — Intra-Op must remain operable)
  - Define and specify degraded performance modes (graceful degradation when full capabilities unavailable)
```

**Context**: Degraded performance modes are particularly important for MFD B's offline capability. The SRS must specify: what features are available when cloud connectivity is lost, how the system behaves when the Pre-Op plan cannot be retrieved, and what patient safety measures are in place when operating in degraded mode. These degraded-mode behaviors must be risk-assessed, not left to implementation decisions.

```yaml
min_iec62304_class: A
applies_to: [Software Development Plan, Product Lifecycle Plan]
verbatim: "Plan must cover the entire product lifecycle. Include provisions for: product deployment, operation, maintenance, and decommissioning."
extracted_requirements:
  - The SDP (or a companion lifecycle plan) must address the full product lifecycle beyond development: deployment, post-market operation, maintenance, and decommissioning
  - Define the planned product lifecycle: expected support period, planned major version cadence, end-of-support criteria
  - Address decommissioning requirements: data archival, patient safety during transition, user notification timeline
```

**Context**: Lifecycle planning is often overlooked in medical device software projects. For MedTech Project, the PCCP extends the product lifecycle by enabling iterative updates without new 510(k)s — the lifecycle plan must account for PCCP change cycles. Decommissioning planning matters because MedTech Project holds surgical case records; data archival obligations under HIPAA and FDA records retention requirements must be addressed.

```yaml
extracted_requirements:
  - Validate MedTech Project in the intended operating environment (or validated simulation) — not just on a development server
  - Validation must demonstrate the product meets all defined user needs and the intended use statement
  - For SaMD with AI components, validation must include clinical performance testing (algorithm performance on representative patient data)
```

**Context**: Validation must be conducted in the intended operating environment — for Intra-Op, this means validation on the actual tablet hardware in an OR-equivalent environment with representative imaging data and representative users. Simulation studies using cadavers, sawbone models, or surgical simulators are acceptable if properly validated as representative. The validation report feeds the 510(k) 510(k) performance testing section and the clinical evaluation.

```yaml
  - Include installation and configuration instructions for the operating environment
  - Document known limitations and contraindications
  - Include security guidance for users: network configuration, access control setup, update process
  - For each PCCP change that modifies user-facing behavior, update the IFU accordingly
```

**Context**: MedTech Project's IFU must document the specific hardware (tablet model), OS version, network requirements, and interfacing systems supported. For cloud-hosted modules (Pre-Op), document browser compatibility. For Intra-Op's offline mode, document the fallback behavior and any user actions required when cloud connectivity is unavailable. Security guidance must cover: how to set up role-based access, how to apply software updates, and how to report security concerns.

<a id="OBL-82304-008"></a>

```yaml
id: OBL-82304-008
title: "Decommissioning Plan"
source: IEC 82304-1:2016 §11
section: "11 — Health Software Product Decommissioning"
scope_flags: [common-baseline]
topic: post-market
artifact_type: plan
dhf_owner: system
min_iec62304_class: A
applies_to: [Product Lifecycle Plan, Post-Market Surveillance Plan]
verbatim: "Plan for orderly decommissioning of the software product. Address data migration, archival, and patient safety during transition. Notify users of decommissioning timeline and alternatives."
extracted_requirements:
  - Define a decommissioning plan covering: data archival (surgical case records, patient data), migration path for active users, patient safety during service transition
  - Define the user notification timeline and process for end-of-support and decommissioning events
  - Address data retention obligations under applicable regulations (HIPAA records retention, FDA MDR records)
```

**Context**: Decommissioning planning is a lifecycle obligation that must be addressed before market release, not at end-of-life. For MedTech Project, surgical case records are clinical records with retention obligations. The decommissioning plan must define what happens to these records if MedTech Project is retired — whether they're exported to the hospital PACS/EHR, held in archival storage, or transferred to a successor product. This must be planned and documented before the first patient case is entered.
