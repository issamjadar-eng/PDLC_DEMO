```yaml
  - role: human-factors
    file_pattern: "*usability-engineering-file*.md"
  - role: risk-management
    file_pattern: "*risk-management-file*.md"
verbatim: "Identify hazards and hazardous situations related to use. Identify potential use errors and their causes. Evaluate the severity and probability of harm from use errors. Feed use-related risks into the ISO 14971 risk management process."
extracted_requirements:
  - Identify all potential use errors per module — perception errors, cognitive errors, action errors
  - Identify the hazardous situation and potential harm sequence for each use error
  - Evaluate severity and probability of harm from each use error
  - Feed use-related risks into the ISO 14971 risk management process (risk inputs, not standalone)
  - Critical use error categories for SaMD: misread measurements, missed alerts, incorrect plan selection, wrong patient data confirmation
```

**Context**: Use-related risk analysis is not a standalone artifact — it feeds directly into the ISO 14971 risk file. Use errors that could cause patient harm must be treated as hazardous situations in the risk file with appropriate risk controls. For MedTech Project, critical use error scenarios include: loading the wrong patient's Pre-Op plan for Intra-Op guidance, misreading anatomical angle measurements, and failing to recognize out-of-bounds guidance warnings.

**Context**: UI verification is primarily a design verification activity (does the built UI match the specification?). source: IEC 62366-1:2015 §5.6
```yaml
section: "5.6 — User Interface Evaluation (Formative)"
scope_flags: [common-baseline]
topic: validation

dhf_owner: both
min_iec62304_class: A
canonical_role: vnv
criticality: must-have
applies_to:
  - role: vnv
    file_pattern: "*formative-evaluation*.md"
  - role: human-factors
    file_pattern: "*usability-engineering-file*.md"
verbatim: "Evaluate the user interface with representative users in representative environments (formative phase). Methods: cognitive walkthrough, heuristic evaluation, usability testing with think-aloud. Can be done with simulated environments and prototype interfaces. Multiple rounds expected."
extracted_requirements:
  - Conduct iterative formative usability evaluations during design
  - Use representative users (or similar proxies) in representative or simulated environments
  - Methods include: cognitive walkthrough, heuristic evaluation, think-aloud usability testing
  - Multiple rounds expected — findings must be fed back into design changes
  - Document findings, design changes made in response, and rationale for accepted vs. deferred findings
```

**Context**: Formative evaluation is the iterative cycle during design — you find problems and fix them before the summative gate. FDA may request formative data in addition to summative results for complex SaMD. For MFD B, formative evaluation in a simulated OR environment is especially important given the high-consequence use environment. Document all rounds even if the immediate finding is "no significant issues" — absence of evidence matters.

```yaml
    file_pattern: "*510k*summative*.md"
verbatim: "Evaluate the user interface with representative users in representative environments (summative phase). Must use production-equivalent device in representative use environment. Must include statistical evidence that critical tasks can be completed safely. Deliverable: Summative Usability Evaluation Report."
extracted_requirements:
  - Conduct a final summative usability evaluation before market release
  - Use production-equivalent device and representative use environment (or validated simulation)
  - Include representative users — matching the intended user profiles defined in §5.1.1
  - Evaluate all critical tasks defined in the UI specification
  - Demonstrate with statistical evidence (task completion rates, error rates) that critical tasks can be completed safely
  - Document: participant profiles, tasks tested, acceptance criteria, results, use errors observed and their root cause
  - Summative Usability Evaluation Report is required in the 510(k) submission for Class II SaMD
```

**Context**: Summative evaluation is the pre-market gate — it must be done with production-equivalent software on representative hardware in a realistic environment. For MFD B, this means an OR-equivalent space with appropriate lighting, a surgical team configuration, and representative patient image data. The summative report is a 510(k) deliverable reviewed by FDA's Human Factors team. Plan for this study early — recruiting representative surgeons takes lead time.

Evaluate any framework-provided UI patterns (modals, data tables, image viewers) that users interact with in clinical workflows.
