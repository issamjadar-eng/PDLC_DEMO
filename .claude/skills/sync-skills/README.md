# sync-skills — Design & Architecture

This document is not loaded by Claude during normal skill operation — it exists for human understanding.

For skill usage and instructions, see `SKILL.md`.

## Best Practices

<!-- Read by /best-practices skill to audit sync hygiene -->

| Check | How to Verify | Severity |
|-------|--------------|----------|
| Sync log exists | `.claude/sync-log.md` exists | Recommended |
| Sync log has a recent entry | Last entry in `.claude/sync-log.md` is within 30 days | Recommended |
| No silent divergence | Running `sync.sh check` returns zero `UPSTREAM_NEWER` entries, OR those entries are documented in the sync log with a rationale (local customization kept intentionally) | Recommended |
| Hitachi path resolves | `sync.sh hitachi-path` exits 0 and points at an existing git repo | Required |
| Script is executable | `.claude/skills/sync-skills/scripts/sync.sh` has the executable bit | Required |
| Allowlist matches installed | Every skill directory under `.claude/skills/` is listed in `project.yml` `security.approved_skills` (and vice versa) | Required |
| No stale sync branches | `sync.sh prune` (dry-run) reports 0 merged `sync/*` branches awaiting deletion — i.e. merged push branches are not accumulating in the hitachi checkout | Recommended |

## Changelog

- 8.3 (2026-05-30): **Windows-clone symlink corruption guard.** Closes a silent corruption vector that propagated registry-wide in PDLC_DEMO (upstream commit `07574e9` overwrote 14 `.claude/agents/*.md` symlinks with 5 KB of agent markdown apiece, preserving filemode 120000; Linux/macOS pulls then failed with `unable to create symlink: File name too long`). Root cause: pre-v8.3 detected symlinks via `[[ -L $path ]]` (filesystem check). On Windows clones, `core.symlinks=false` is the git default — tracked symlinks materialize as plain text files containing the target path string, so `-L` returns false. The script took the regular-file branch, hashed the path-string as arbitrary content, mismatched every upstream symlink blob, reported false UPSTREAM_NEWER drift, and (worst case) overwrote the path-string content on pull → git recorded the new bytes under the preserved 120000 index mode → push propagated the corruption. Fixes in three places:
  1. **New `_is_tracked_symlink` helper** consults the git index (`ls-files -s` mode == 120000) rather than the filesystem — authoritative across OS / `core.symlinks` settings.
  2. **New `_smart_content_hash` helper** computes effective resolved-content hash across all storage layouts: real symlink (follow), regular file not tracked-as-symlink (hash bytes), and Windows-style materialization (resolve target string manually and hash the resolved file). Falls back to a unique sentinel hash for corrupt/unresolvable cases so drift is always reported. `cmd_analyze` and `_walk_registry_tree` both switched to this helper — eliminates the v8.1 sha1sum-via-< compare's blind spot for Windows materialization while preserving its "compare resolved content regardless of layout" semantics (all 4 v8.1 cases still pass).
  3. **`cmd_push_stage` hard guard** — refuses to stage a file that's tracked as mode 120000 in the project index but whose on-disk content is implausible as a symlink target (multiline or > 4096 bytes / PATH_MAX). Exits 8 with a multi-line remediation message naming the Windows clone as the likely source and giving the `git config --global core.symlinks true` fix. This is the bullet-stopper — even if the Windows clone produces corrupted blobs locally, they cannot land in a sync PR.
  4. **New `tests/test_windows_symlink_guard.sh`** — 4 cases simulating the Windows on-disk state by `rm`-ing a real symlink and writing a regular file with the target string as content (index still mode 120000, WT is regular file): clean materialization → no false drift; corrupted oversized → push refused; corrupted multi-line → push refused; real Linux symlink → push succeeds (no false-positive refusal). All 4 v8.1 `test_symlinks.sh` cases + 11 status + 10 three_way_pull + 15 prune all still green (44 assertions total).
  **Post-update:** No setup re-run required. No new hooks, no schema change. The fix is additive — `_smart_content_hash` is a strict superset of v8.1's sha1sum behavior for non-Windows cases. Any project whose `.claude/agents/` was corrupted by the same bug class should be repaired via git plumbing (use `git update-index --cacheinfo 120000,<blob>,<path>` to restore the correct symlink target blob; see PDLC_DEMO PR #11 for a worked example). Run `bash .claude/skills/sync-skills/tests/test_windows_symlink_guard.sh` to validate locally.

- 8.2 (2026-05-16): **Push branches no longer accumulate — auto-clean on `--merge` + a new `prune` action.** `push-prep` creates a `sync/<topic>-<date>` branch for every push and nothing deleted the local copy, so they piled up in the hitachi checkout (one cleanup cleared 111). Two fixes: (1) the `push` action's Step 5b (`--merge` path) now runs `git -C <hitachi> branch -D <branch>` after the fast-forward — the `gh pr merge --delete-branch` only removed the *remote* branch, this removes the leftover *local* one, so every `--merge` push self-cleans. (2) New **`prune`** action + `sync.sh prune [--apply]` subcommand: classifies every `sync/*` branch (local ∪ remote) against `main` via `git cherry` — MERGED (content in main) vs UNMERGED (genuinely unmerged or superseded). Dry-run by default; `--apply` deletes the MERGED branches on both sides; UNMERGED branches are surfaced by name and never auto-deleted. Covers the PR-only push path (merged out-of-band, which auto-clean can't see) and pre-existing residue. `status` block 5 now also notes a stale-`sync/*`-branch count (hygiene only — does not affect the SYNCED verdict). New `tests/test_prune.sh` — 15 assertions over dry-run classification, `--apply` deletion (local + remote), idempotence, and the empty case.
  **Post-update:** No setup re-run required — no new hooks, no schema change. One-time: run `/sync-skills prune` to clear any `sync/*` branches that accumulated before this version.

- 8.1 (2026-05-02): **Symlink-aware drift detection in `cmd_check` (and `cmd_analyze`).** Pre-fix, `check` hashed `git show <ref>:<path>` (which for a symlink — git mode `120000` — returns the link TARGET STRING, not its resolved content) against `sha1sum <local-path>` (which follows symlinks and hashes the resolved file). Two failure modes: (a) every git-tracked symlink with matching content reported perpetual `UPSTREAM_NEWER` drift (false positive); (b) when one side was a symlink and the other a regular file but resolved content matched, drift was correctly suppressed by accident — but only because the buggy compare happened to match for that specific layout, not by design. The first failure was the visible one; surfaced in the field when `agents/<name>.md` (a symlink → `../skills/<owner-skill>/agents/<name>.md` in both upstream and local) reported perpetual drift after a clean pull, even with `md5sum` showing identical resolved content. Fix: `cmd_check` now uses filesystem-cat compare on both sides — `< file` redirection follows symlinks transparently — so what's compared is the resolved content, regardless of layout. Unifies all 4 storage combinations (regular↔regular, regular↔symlink, symlink↔regular, symlink↔symlink) under one semantic: "do they have the same effective content?" — which is what users mean by "in sync" and what `pull` (which copies resolved bytes via `cp`) would produce. Trade-off: upstream side now read from the hitachi WORKING TREE rather than `git show <ref>`; that's already an invariant elsewhere in the script (push-prep resets to origin/main, pull copies from working tree). `cmd_analyze` got a parallel fix: when `local_path` is a symlink, hash the readlink output via `git hash-object --stdin` (matching how git stores symlink blobs) instead of `git hash-object <path>` (which follows the symlink). New `tests/test_symlinks.sh` driver — 4 cases (both-symlinks-same-target, both-symlinks-different-target-same-content, type-mismatch-same-content, both-symlinks-divergent-content) all pass. All 21 existing tests in `test_status.sh` + `test_three_way_pull.sh` remain green.
  **Post-update:** No user action required. The fix is purely additive — non-symlink paths are unaffected (the both-regular branch is byte-for-byte equivalent to v8). Anyone whose project has agents or scripts wired in via symlinks (e.g., `.claude/agents/<name>.md` → `.claude/skills/<owner>/agents/<name>.md`) will see drift counts go to zero where the resolved content is in sync. Run `bash .claude/skills/sync-skills/tests/test_symlinks.sh` to validate the new behavior locally.
- 8 (2026-05-01): **Three-way merge analysis on `pull` — UPSTREAM_NEWER files are bucketed before any auto-apply.** Closes the loop on a real incident: a blanket-approve `pull` clobbered 1131 lines of un-pushed local work because every UPSTREAM_NEWER file was treated as "upstream is newer → fast-forward," when in fact the local copies were newer. The pre-v8 `check` had no way to tell which side was actually newer. v8 adds a per-file `analyze` subcommand and a `check --analyzed` flag that probe the hitachi blob history for each UPSTREAM_NEWER path and emit one of four recommendations: **UPSTREAM_ADVANCE** (local matches an old hitachi blob; upstream advanced cleanly — safe auto-pull), **LOCAL_AHEAD** (local blob unknown to hitachi AND project edited within 7 days — keep local, push candidate, NEVER auto-pull), **BOTH_DIVERGED** (both sides advanced — manual diff review per file), or **UNDETERMINED** (probe failed — treated as BOTH_DIVERGED for safety). The `pull` action now runs `check --analyzed` first and presents three buckets: an Auto-pull bucket (UPSTREAM_ADVANCE + UPSTREAM_ONLY), a Skip bucket (LOCAL_AHEAD — surfaced as push candidates), and a Confirm bucket (BOTH_DIVERGED + UNDETERMINED — per-file Y/N gate with diff). Default action is "approve auto-pull bucket only." Implementation: pure git probes (`hash-object`, `log --all`, `ls-tree`, `rev-list --count`) — no state file. Fall-through to UNDETERMINED on any probe failure so pull never crashes. New `tests/test_three_way_pull.sh` driver with 4 cases (UPSTREAM_ADVANCE, LOCAL_AHEAD, BOTH_DIVERGED, mixed batch including UPSTREAM_ONLY) and 10 assertions. All 11 v7 tests still pass — total 21.
  **Post-update:** No user action required. The new `--analyzed` flag is opt-in for the script CLI but is now mandatory in the `/sync-skills pull` action narrative. Existing `check` (without `--analyzed`) still emits the unenriched 2-column format for backward compat. Re-run `bash .claude/skills/sync-skills/tests/test_three_way_pull.sh` to validate locally.
- 7 (2026-05-01): **New `status` action — at-a-glance "are all four places in lockstep?" health check.** Reports five labeled blocks: project working tree (clean/DIRTY), project HEAD vs origin (SYNCED/AHEAD/BEHIND/DIVERGED/NO UPSTREAM), registry working tree, registry HEAD vs origin, and skill drift (count of LOCAL_ONLY/UPSTREAM_ONLY/UPSTREAM_NEWER from the existing `check` primitive). Final line is `Overall: SYNCED — safe to switch machines` or `Overall: NOT SYNCED — see <which block> above`. Read-only (only `git fetch --quiet`); exits 0 when SYNCED, 1 otherwise. Edge cases handled: missing hitachi clone, no upstream tracking, working tree dirty + HEAD synced (still flagged as DIRTY), branch on a non-main branch (tracks the branch's actual upstream). New `tests/test_status.sh` driver builds a self-contained world (fake project + fake registry + bare remotes) and exercises 4 cases (all-synced, dirty, ahead, drift) with 11 assertions. Honors `STATUS_NO_FETCH=1` for offline test runs.
  **Post-update:** No user action. New action is purely additive — existing `check`, `pull`, `push`, `sync` flows are untouched. Run `bash .claude/skills/sync-skills/scripts/sync.sh status` (or invoke via the skill) any time before switching machines or kicking off a long push.

- 5 (2026-04-16): **Portable SHA-1 in `check`.** Script previously used `shasum -a 1` exclusively (a Perl script that ships on macOS and Debian/Ubuntu but is missing from minimal Linux images like Alpine and some slim Docker bases). On systems without Perl or `shasum`, every `UPSTREAM_NEWER` diff would fail and skip silently. Switched to a prefer-`sha1sum` runtime detect (GNU coreutils, always on Linux), falling back to `shasum -a 1` when `sha1sum` is unavailable (covers macOS default + Debian/Ubuntu without coreutils). Content equality is the only property used, so either hash family is equivalent. Discovered during task 067 cross-platform audit.
  **Post-update:** No user action. `check` continues to work byte-for-byte on mac + WSL Ubuntu (same output), and now also works on minimal Linux bases.
- 4 (2026-04-15): Local file walk now uses `git ls-files -co --exclude-standard` instead of raw `find`, so `.gitignore` is honored. Prevents build artifacts (`__pycache__/`, `*.pyc`, `.DS_Store`, virtualenv trees) from polluting the diff report or from sneaking into a `push-stage` copy. Upstream walk was already git-based, so this makes the two walks symmetric. (Backfilled entry — the change landed in the script upstream but wasn't recorded in the changelog at the time.)
  **Post-update:** No user action. The new walk is a strict subset of the old one — anything that showed up before still shows up, but nothing in `.gitignore` will leak through.
- 3 (2026-04-13): `pull` now performs mandatory Project Impact Analysis (new Step 5b) after every successful file pull. For each pulled file, Claude reads the updated changelog and any `**Post-update:**` annotations, then produces a Project Impact Report covering setup re-runs, template regeneration, best-practices table diffs, frontmatter/schema changes, terminology renames, and hook changes. Applies to single-file pulls too — silence is not acceptable. Rationale: previously, a pull could land a new-behavior skill version without Claude surfacing what the project needed to do to align. Now alignment analysis is part of what pull *means*.
  **Post-update:** No user action. The new Step 5b executes automatically on the next `/sync-skills pull` or `/sync-skills sync`.
- 2 (2026-04-12): Added opt-in `--merge` flag to `push`. When passed, the skill calls `gh pr merge --squash --delete-branch` after the PR is created, then `git pull --ff-only` in the local hitachi checkout so it stays in sync. Default remains PR-only — never merge without explicit request.
