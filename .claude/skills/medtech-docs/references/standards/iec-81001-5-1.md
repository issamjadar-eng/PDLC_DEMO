**Category**: Cybersecurity
**Recognized by FDA**: Yes — referenced in FDA Cybersecurity guidance as a recognized standard

## Overview

IEC 81001-5-1 defines the security activities required throughout the software development lifecycle for health software. It is the lifecycle-process companion to the threat-focused approach in AAMI TIR57, providing specific process requirements for building security into software from the start.

## Key Process Requirements by Clause

### Clause 4 — General Requirements

#### 4.1 Quality Management
- Security activities must be part of the quality management system
- Assign security roles and responsibilities
- Ensure security competence of personnel

#### 4.2 Security Risk Management
- Integrate security risk management into the overall risk management process (ISO 14971)
- Security risk management must consider: confidentiality, integrity, availability
- Apply throughout the entire lifecycle

### Clause 5 — Software Development Process Security Requirements

#### 5.1 Software Development Planning — Security
- Include security activities in the software development plan
- Plan must address: threat modeling, secure design principles, security testing, vulnerability management
- Define security requirements sources (regulatory, standards, organizational policies)
- **Deliverable**: Security section of Software Development Plan

#### 5.2 Health Software Requirements — Security
- Derive security requirements from:
  - Security risk assessment
  - Regulatory requirements (FDA cybersecurity guidance)
  - Intended use environment threat landscape
  - Data protection requirements (PHI/PII if applicable)
- Security requirements must cover:
  - Authentication and access control
  - Authorization and privilege management
  - Audit logging and accountability
  - Data confidentiality (at rest and in transit)
  - Data integrity
  - Secure communication
  - Software update/patch mechanisms
  - Cryptographic controls
- **Deliverable**: Security Requirements (as part of SRS)

#### 5.3 Software Architectural Design — Security
- Apply secure design principles:
  - Defense in depth
  - Least privilege
  - Secure defaults
  - Fail secure
  - Separation of duties
  - Minimize attack surface
- Document security architecture decisions
- Identify trust boundaries between components
- **Deliverable**: Security Architecture (as part of SAD)

#### 5.4 Software Design — Security
- Apply secure coding practices
- Address common vulnerability categories (OWASP, CWE)
- Review design for security weaknesses

#### 5.5 Software Implementation — Security
- Follow secure coding standards
- Use static analysis tools to detect vulnerabilities
- Perform code reviews with security focus
- Manage third-party components (SOUP) for known vulnerabilities

#### 5.6 Software Integration Testing — Security
- Test security controls at integration points
- Verify security of interfaces between components
- Test authentication, authorization, and encryption at integration boundaries

#### 5.7 Software System Testing — Security
- Conduct security testing of the complete system:
  - Vulnerability scanning
  - Penetration testing
  - Fuzz testing
  - Security regression testing
- Test against known vulnerability databases (CVE, NVD)
- **Deliverable**: Security Test Report

#### 5.8 Software Release — Security
- Document known security vulnerabilities and mitigations
- Provide security guidance for deployment
- Generate Software Bill of Materials (SBOM)
- **Deliverable**: SBOM, Security Release Notes

### Clause 6 — Software Maintenance Process — Security

#### 6.1 Security Monitoring
- Continuously monitor for new vulnerabilities affecting the software and its components
- Monitor vulnerability databases and SOUP vendor advisories
- Establish a coordinated vulnerability disclosure process

#### 6.2 Security Patch Management
- Establish a process for evaluating and deploying security patches
- Prioritize patches based on severity and exploitability
- Test patches before deployment

#### 6.3 End-of-Support Planning
- Define end-of-support timeline for the software product
- Plan for secure decommissioning
- Communicate end-of-support to users

### Clause 7 — Security Risk Management Process

#### 7.1 Threat Modeling
- Identify assets (data, functions, interfaces)
- Identify threat agents (malicious users, malware, insider threats, network attackers)
- Identify threats using a systematic method (STRIDE, attack trees, etc.)
- Identify vulnerabilities that could be exploited

#### 7.2 Security Risk Assessment
- Estimate the likelihood of exploitation
- Estimate the impact on safety, effectiveness, and data security
- Evaluate risk against acceptability criteria

#### 7.3 Security Risk Control
- Implement security controls to mitigate identified risks
- Verify the effectiveness of security controls
- Evaluate residual security risk

### Clause 8 — Configuration Management — Security

- Track security-relevant configuration items
- Manage access to source code and build systems
- Maintain integrity of the build and release pipeline
- Ensure reproducible builds

### Clause 9 — Problem Resolution — Security

- Establish a security incident response process
- Define severity classification for security issues
- Track security problems to resolution
- Report security incidents per regulatory requirements

## SBOM Requirements

Per FDA cybersecurity guidance and NTIA minimum elements:
- SBOM must include: component name, version, supplier, dependency relationship, author, timestamp
- Machine-readable format required (SPDX or CycloneDX)
- Must cover all software components including SOUP/third-party libraries
- Must be kept current through the product lifecycle
