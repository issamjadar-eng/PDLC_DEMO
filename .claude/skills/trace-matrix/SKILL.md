# Trace Matrix Skill

Build the bidirectional design-controls trace matrix for any DHF in a medtech-docs project. Usage: `/trace-matrix <action>`

This skill is the **writer**. It parses the design-controls source docs of each DHF, computes the trace graph (UN ↔ DI ↔ SW ↔ Architecture ↔ V&V, with Risk as an overlay), detects orphans and broken references, and emits two artifacts atomically per DHF into the **project-console working area**:

- `docs/project/console/<dhf-name>/console_trace_matrix.md` — human-readable rendering of the trace graph (the *console* working copy — **not** a controlled regulatory deliverable).
- `docs/project/console/<dhf-name>/console_trace_matrix.json` — structured sidecar consumed by `project-console`'s Trace Matrix section.

The output is intentionally **outside** the DHF documentation tree (`docs/project/dhfs/<leaf>/design-controls/trace-matrix/` for system DHFs; `docs/project/_confluence/<arch_slug>/...` for item DHFs in projects that mirror Confluence). Those folders are reserved for *controlled* trace-matrix deliverables authored through document control. The console copy is for project-management and tooling, regenerates on every build, and is committed so a fresh `git pull` + `/project-console run` shows the last-saved state without re-running the pipeline.

The sidecar JSON is the contract. The skill knows nothing about the console; the console knows nothing about this skill. They cooperate via the JSON shape + the file-system convention `docs/project/console/<leaf>/console_trace_matrix.{md,json}`.

Per-DHF override: a project may set `output_dir:` on a DHF in `trace-matrix.yml` to redirect the output. If you do, also update the project-console loader's `_CONSOLE_BASE` so the reader still finds the sidecar.

## Adapter model (v3, shared cross-layer adapters)

Different projects author their source docs differently — column headers, ID formats, table shapes, and even file layouts vary. Rather than forcing every project to conform to one hardcoded parser, this skill uses a three-tier adapter model:

| Tier | Location | Written by | When used |
|---|---|---|---|
| **Shared adapters** | `${CLAUDE_SKILL_DIR}/scripts/parsers/<name>.py` | Shipped with the skill | When a layer's `trace-matrix.yml` config sets `adapter: <name>` |
| **Project adapters** | `${CLAUDE_PROJECT_DIR}/tools/project-console/trace-matrix/adapters/<layer>.py` | Generated by `/trace-matrix init` or edited by hand | When the per-layer override file is present |
| **Default adapters** | `${CLAUDE_SKILL_DIR}/scripts/parsers/defaults/<layer>.py` | Shipped with the skill | Fallback when no override resolved |

All three expose the same tiny interface:

```python
def parse(path: Path, layer_cfg: dict) -> ParserResult
```

Resolution order in `adapter_api.load_adapter`: explicit `adapter:` name → project override → default. The **build is always deterministic** — adapters are imported by file presence, never generated at build time. LLM/analysis work happens only during `init`, which produces files on disk that subsequent builds import directly.

### Shared adapters (project-agnostic, cross-layer)

| Adapter | Layers it can serve | What it parses |
|---|---|---|
| `jira-mirror` | `design_inputs`, `software`, `vnv`, `risk` | GFM tables emitted by the `jira-pull` skill under `docs/project/_jira/<arch>/<version>/{epics,stories,hazards,tests}.md`. Auto-detects shape from the table headers (`DI Prefix`, `Parent`, `Verifies`, `PHA Prefix`). Cells of the form `[KEY](URL)` are flattened to `KEY` and the URL captured in `source_ref` for back-linking. |

## Default layer source convention

| Layer | Default source within a DHF | Default ID prefix | Notes |
|---|---|---|---|
| User Needs | `design-controls/user-needs/user-needs.md` | `UN` | Top of trace |
| Design Inputs | `design-controls/requirements/design-inputs.md` | `DI` | Carries both UN upstream edges and V&V downstream edges (from the Verification Method column) |
| Software Requirements | _(optional, no default source)_ | _(project-defined)_ | Empty by default. Item DHFs whose software requirements live in a separate artifact (e.g. Jira Stories) configure `software:` with `adapter: jira-mirror` or a project adapter |
| Architecture | `design-controls/architecture/<dhf>-system-sad.md` | `M` | v1: nodes-only — Module ↔ DI mapping table is not required to exist; layer renders with `edges_known=false` if absent |
| V&V | `null` (derived from DI verification column) | `VER` | When a real `verification-protocols.md` exists, set `source:` in `trace-matrix.yml` — the adapter override can read it directly |
| Risk | `risk-management/<source>` | `HZ` | If source is empty or an `awaiting-content` placeholder, layer renders with `source_empty` |

All defaults are overridable per DHF in `trace-matrix.yml`. For structural divergences a project adapter file in `tools/project-console/trace-matrix/adapters/` takes over entirely.

## Edge model — bidirectional authoring (since v8)

Each layer-pair relationship is treated as an undirected logical link that either side may author. Adapters populate one or more of three authoring fields on each node; the engine collects every claim into a canonical `(upstream_id, downstream_id)` edge set, dedupes when both sides author the same relationship, and builds the rendered edge plus per-item forward/reverse lists from that set.

| Field on item | Convention | Read as |
|---|---|---|
| `traces_forward_ids` | child-points-up | "the upstream parent(s) I trace to" |
| `verifies_di_ids` | child-points-up (legacy) | "the DI parent(s) I verify" — emitted by the default DI parser onto V&V nodes |
| `verification_ids` | parent-points-down | "the V&V child(ren) that verify me" — emitted from DI rows' or SW rows' Verification Method column |

Adapter authors only set the fields the source doc actually supports. The engine does not require both sides to author the same relationship — one side is enough to build the edge. When both author the same relationship, the canonical set dedupes naturally.

### V&V scope filter

When the V&V layer has its own source files (jira-mirror, or a real verification-protocols doc), the engine runs a narrow scope filter: V&V items whose authored upstream targets do not resolve to any requirement-layer node (DI or SW) are dropped, and a `scope_filter` warning is recorded on the V&V layer. This keeps test-execution mirrors scoped to "tests that verify requirements" rather than the full execution universe (which a Jira mirror may include defect-fix tests, hazards-only tests, etc.).

The filter does **not** run when V&V is DI-derived (no V&V source files). In that case every VER node is a DI-verifying node by construction — filtering would drop legitimate trace data.

### Asymmetric-trace warnings

When V&V has an independent source AND a parent (DI or SW) references a VER that authors other upstream claims but does not reciprocate the parent's claim, the engine emits an `asymmetric_trace` warning on the V&V layer. The warning surfaces inconsistent authoring (e.g., DI lists a VER in its verification column, but the VER's own "Verifies" column points at different requirements) so a human can reconcile. Both authored edges still build — the warning is informational, not a broken_ref. DI-derived V&V is silent here for the same reason the scope filter is silent: there is no independent VER source to disagree.

### `trace-matrix.yml` per-layer fields

```yaml
- name: <dhf-leaf>
  layers:
    <layer-key>:                 # one of: user_needs, design_inputs, software, architecture, vnv, risk
      source: <repo-relative path or list of paths>
      id_prefix: <prefix>        # e.g. DI, UN, PHA — used for prefix-based filtering and rational-check
      adapter: <shared-name>     # OPTIONAL — invokes scripts/parsers/<name>.py instead of the per-layer default
      columns: { ... }           # OPTIONAL — column-name overrides honoured by the layer's parser
```

When `adapter:` is set, it takes priority over the project override and the default. A typical item-DHF block sourced from a Jira mirror:

```yaml
- name: <item-dhf>
  layers:
    design_inputs:
      source: docs/project/_jira/<arch>/v1.0.0/epics.md
      id_prefix: DI
      adapter: jira-mirror
    software:
      source: docs/project/_jira/<arch>/v1.0.0/stories.md
      id_prefix: <jira-project-key>
      adapter: jira-mirror
    vnv:
      source: docs/project/_jira/<arch>/v1.0.0/tests.md
      id_prefix: <jira-project-key>
      adapter: jira-mirror
    risk:
      source: docs/project/_jira/<arch>/v1.0.0/hazards.md
      id_prefix: PHA
      adapter: jira-mirror
```

## JSON Sidecar Contract (v1.1)

```json
{
  "version": "1.1",
  "dhf": "<DHF name>",
  "generated_at": "2026-04-15T...",
  "layers": [
    {
      "key": "user_needs",
      "title": "User Needs",
      "id_prefix": "UN",
      "source_files": ["docs/project/dhfs/<dhf>/design-controls/user-needs/user-needs.md"],
      "items": [
        {
          "id": "UN-001",
          "summary": "...",
          "full_text": "...",
          "category": "CLIN",
          "criticality": null,
          "group": "G1",
          "stakeholder": "...",
          "priority": "High",
          "source_ref": "...",
          "traces_forward": [
            {"id": "DI-001", "summary": "..."}
          ],
          "traces_reverse": []
        }
      ],
      "missing_reason": null,
      "edges_known": true,
      "warnings": []
    }
  ],
  "edges": [{"from": "UN-001", "to": "DI-001"}],
  "gaps": {
    "orphans": {"user_needs": [], "design_inputs": [], "vnv": [], "architecture": [], "risk": []},
    "broken_refs": [],
    "empty_layers": []
  },
  "stats": { ... }
}
```

The sidecar is **self-contained** — labels and full text are inlined per item so the console can render expandable rows without a second fetch. `source_files` lets the console build "↗ View in source" links without hardcoding any paths.

## Actions

Parse the user's argument string `$ARGUMENTS` to determine which action to perform.

### `init`

First-time setup. Idempotent — safe to re-run.

**Steps**:
1. Read `project.yml` and enumerate `dhfs[]`.
2. If `trace-matrix.yml` does not exist, write a default one mapping each DHF's layers to the conventional source paths.
3. For each DHF × layer, run `python ${CLAUDE_SKILL_DIR}/scripts/analyze.py --dhf <name> --json` to get per-layer rational-check verdicts.
4. For each layer whose verdict is `ok: false` **with a non-empty source** (a parser problem, not a data gap):
   - Read the source document directly.
   - Generate a Python adapter file tailored to that document's observed shape (column headers, ID format, trace column semantics, etc.). The adapter must expose `def parse(path, layer_cfg) -> ParserResult`.
   - Write it to `tools/project-console/trace-matrix/adapters/<layer>.py`.
   - Append a rationale block to `tools/project-console/trace-matrix/analysis-notes.md`: what the defaults returned, what the source actually looks like, what the generated adapter does differently.
5. Run `python ${CLAUDE_SKILL_DIR}/scripts/build.py --repo ${CLAUDE_PROJECT_DIR}` and confirm no regressions.
6. Print a summary: which layers used defaults, which got generated adapters, which still have data gaps that no adapter can fix.

**Flags**:
- `--regenerate` — force re-generation of existing adapters. Without this, init never overwrites a project adapter file.
- `--dhf <name>` — restrict to one DHF.
- `--layer <key>` — restrict to one layer (requires `--dhf`).

### `build [--dhf <name>] [--check]`

Parses sources via the resolved adapters, computes the graph, writes outputs. **Deterministic — no LLM.**

**Steps**:
1. Read `trace-matrix.yml`.
2. For each DHF (or just `--dhf <name>`):
   - Resolve the adapter for each layer via `load_adapter`.
   - Run parsers against the configured sources.
   - Build the graph; compute orphans, broken refs, reverse edges.
   - Emit `trace-matrix.md` and `trace-matrix.json` atomically.
3. With `--check`: do everything except write. Exit 1 if any gap is found.
4. Print a per-DHF summary table to stdout showing layer counts, orphans, and whether each layer used `[deflt]` or `[proj]` adapter.

### `check`

Alias for `build --check`. Hook/CI friendly.

### `analyze`

Run the rational check against the currently resolved adapters and print a verdict, without any other side effects. Useful for debugging "why did my source doc not parse?"
