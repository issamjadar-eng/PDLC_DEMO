## Question

Process-validation and calibration posture — overdue and due items by site and product line, and the blockers for PP3500 rev C release.

**Asked by**: vp-quality, plant-manager · **cadence**: weekly

## Goal — the decision this answer serves

The weekly plant / quality review: which overdue instruments come out of service and
which lots need an impact assessment, which validations are due, and what must close
before PP3500 rev C can be released cleanly — and whether rev C lots have already gone
out ahead of that. The answer joins the validation register with the lot records so the
release question is answered from both sides.

## Approach

Operational definitions this answer commits to:

- **As-of** = the pinned validation snapshot's provenance `as_of`.
- **Statuses are read from the register as recorded** (`validated | due | overdue |
  in-progress | not-started`, vocabulary-asserted); the register derives them against
  its own data horizon, which equals the as-of. **Days overdue** = as-of − `due_date`.
  The **due-soon window** is `due_soon_days` (catalog `params`, 30) and is the
  register's `due` status.
- **Cuts**: overdue and due-soon counts by site, by record type, and by product line
  (empty product line = shared equipment, reported as `shared`); overdue calibrations
  listed individually with days overdue.
- **Rev C blockers, validation side** = records with `product_line == PP3500` whose
  `asset_or_process` names "rev C" and whose status is not `validated`.
- **Rev C blockers, lot side** = `internal-production-lots` rows with `product_line ==
  PP3500` and `hw_rev == C`: **released** = `release_date` set; **in process** =
  unreleased with `dhr_complete == true`; **blocked** = unreleased with `dhr_complete ==
  false`. The first release date is the minimum `release_date`.
- **Released-while-open** = released rev C lots exist AND a rev C fixture PQ is not
  validated — a computed comparison, reported with the caveat that neither pin records
  which fixture tested each lot.
- **History** = not computable from one snapshot of a status register; published as an
  `unavailable` series naming the refresh cadence that would build it.

## Data

Registered corpus dependencies:
- `manufacturing/internal-process-validation` (IQ / OQ / PQ, calibration, PM records:
  asset or process, product line, site, status, completed / due dates, owner)
- `manufacturing/internal-production-lots` (rev C lot release state and DHR
  completeness)

Data we have: both pins as-of 2026-08-31. Data we still need (stated gaps, never faked):
which test fixture ran each lot (to settle the released-while-open question), the
design-transfer plan's validation-before-release gate text, the calibration procedure's
lot-impact rule, and prior snapshots for a posture trend.

## Assumptions & expectations

- **E-08.1** — No production measuring equipment is past its calibration due date
  _(basis: stand-in; the calibration procedure on record is not distilled in this
  project's sources [VERIFY])_. Verdict rule: met if zero calibration records carry
  status `overdue`.
- **E-08.2** — PP3500 rev C lots are released only after the rev C test-fixture PQ is
  complete _(basis: stand-in; the design-transfer plan's validation-before-release gate
  is not distilled in this project's sources [VERIFY])_. Verdict rule: not-met if any rev
  C fixture PQ is not validated while at least one rev C lot is released.
- **Rollup-survival rule**: the verdict headline carries the overdue and due-soon counts,
  overdue calibrations per site, every open rev C validation item with status and due
  date, the blocked-lot count, and the released-while-open count with the first release
  date.

## Assertions & limits

This answer asserts: register posture counts by site / type / line, each overdue
calibration with days overdue, the open rev C validation items, and the rev C lot
release state. It does **not** assert: that released rev C lots were tested on the
unvalidated fixture (the routing is not in either pin — it is a question to the DHRs),
the lot impact of an overdue instrument (needs the instrument-to-lot usage log), a
posture trend (single snapshot), or that the gates are correct (both expectations are
unvalidated).
