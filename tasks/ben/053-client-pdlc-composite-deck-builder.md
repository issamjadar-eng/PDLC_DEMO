## Goals

Build a new `assets/client-pdlc/` composite presentation that mechanically harvests every slide from the three existing decks and lets the user curate them into a final deliverable through a browser-based editor.

**Source decks** (slide counts captured Phase-0, 2026-05-13 — confirmed against `<section class="slide ...">` containers; earlier estimate of ~252 was inflated because `grep class="slide..."` also matched the inner `<div class="slide-content">` element):
- `assets/agentic-delivery/index.html` — 47 slides, 312 KB, 105 KB inline CSS, body chrome (`.progress-bar`/`.nav-dots`/`.keyboard-hint`) to exclude, Google Fonts via `<link>` to preserve
- `assets/project-overview/index.html` — 52 slides, 160 KB, 35 KB inline CSS, no body chrome, no externals
- `assets/project-overview-2/index.html` — 27 slides, 115 KB, 58 KB inline CSS, one image at `assets/project-overview/console-01-landing.png` (rewrite to `../project-overview/console-01-landing.png` when emitting under `assets/client-pdlc/`)
- **Total candidate pool**: 126 slides

**Deliverables**:
1. `assets/client-pdlc/candidate.html` — editable composite of all slides from the three sources, with per-slide controls:
   - **Reorder** — drag-and-drop (or move-up / move-down buttons) to change slide position
   - **Mark keep / remove** — toggle that flags a slide for inclusion or exclusion in the final
   - **Persist state** — selections + ordering survive page reload (localStorage minimum; ideally exportable as a `picks.json` sidecar so the curation is committable)
   - Reasonable visual differentiation (e.g., dimmed/striked-through "remove" slides; source-deck badge per slide)
2. `assets/client-pdlc/index.html` — generated final deck containing only `keep`-marked slides in the user's chosen order, in the same single-file viewable shape as the source decks (self-contained CSS, navigable like the originals)
3. **Generate action** — a button or one-shot tool that reads the current curation state and writes `index.html`. Could be in-browser (Save As / download), or a tiny Python script in the task that consumes `picks.json` + the source HTMLs and emits the final.

**Mechanical harvest only** — no re-rendering, no markdown source. Pull each `<section class="slide ...">` (or equivalent slide container) verbatim from the three source `index.html` files. Inline CSS / scoped CSS from each source must be carried along so each slide renders correctly when interleaved (this is the main technical question — see Open Questions).

## Open Questions (resolve before Phase 1 build)

<!-- STRATEGY CONTENT: architecture, css-isolation -->
1. **CSS-isolation strategy. RESOLVED 2026-05-13: scoped CSS per source.** Wrap each slide in `<div class="src-{deck}">` and prefix every rule from that deck's `<style>` block with `.src-{deck}`. Single-page DOM, easy drag-reorder, no iframe overhead. Considered + rejected: (b) iframe-per-slide (250 iframes too heavy + nav glue), (c) Shadow DOM per slide (more moving parts for negligible isolation gain over option a). Build.py CSS-rewriter must handle: `@media`, `@keyframes` (don't prefix), `:root` / `--*` custom properties (rewrite to scope), `html` / `body` selectors (rewrite to the scoping div).
<!-- /STRATEGY CONTENT -->
<!-- STRATEGY CONTENT: architecture, picks-schema -->
2. **State serialization shape. RESOLVED 2026-05-13: flat ordered list, schema `client-pdlc/picks@1`.** Shape: `{schema, sources:{name→path}, order:[{src, idx, keep}, …]}`. The `order` array is the source of truth — its sequence == final slide sequence; `keep:false` slides are retained in the list so the curator can flip them back on without losing position. Localstorage in candidate.html mirrors this exact shape. Considered + rejected: per-source maps + order array (over-normalized for this workflow), reusing `md-deck/picks@2` (modeled for markdown anchors + creative cache, wrong fit).
<!-- /STRATEGY CONTENT -->
<!-- STRATEGY CONTENT: architecture, generator-flow -->
3. **Generator flow. RESOLVED 2026-05-13: standalone `assets/client-pdlc/build.py` reads committed `picks.json`.** Two actions: (a) `build.py --candidate` re-emits `candidate.html` from the three source decks (idempotent; safe to re-run if a source deck changes); (b) `build.py --final` reads `picks.json` and emits `index.html` containing only `keep:true` slides in the `order[]` sequence. In-browser flow: candidate.html persists state in localStorage, "Export picks.json" button downloads the file, user drops it into `assets/client-pdlc/picks.json`, then runs `build.py --final`. Both `picks.json` and `index.html` are committable artifacts — final deck is fully regenerable from git.
<!-- /STRATEGY CONTENT -->

4. **Initial slide order in candidate.html. RESOLVED 2026-05-13: agentic-delivery → project-overview → project-overview-2.** Total 94 + 104 + 54 = 252 slides in that sequence, all marked `keep:true` by default. Curator reorders / drops slides from there.
